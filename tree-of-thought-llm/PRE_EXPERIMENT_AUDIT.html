Executive summary

The implementation is close to ready. Search logic, pruning, candidate generation, and instrumentation are correctly shared across A/B/C/D within each benchmark — the four conditions differ only in the backtrack-target function, exactly as intended. Two things need your attention before freezing, both read-only findings, not code changes:

Correction to your own framing — please re-read before writing the methodology section

Your prompt describes Condition B as: "no longer allows arbitrary fallback to an immediate parent... if no non-parent recoverable level exists, the branch is treated as unrecoverable / returns to root." That describes Condition D, not B. Per the current code:

  • B's prompt explicitly keeps the parent as an always-legal fallback — dfs.py:248, dfs_crossward.py:321-324: "If no step beyond the immediate parent is recoverable, return the immediate parent. The immediate parent is the fallback and is always an acceptable answer." B has no UNRECOVERABLE concept at all.
  • D is the one that forbids the parent and can go unrecoverable — and "unrecoverable" does not mean "returns to root and keeps searching." It means the sentinel -1 propagates through every enclosing stack frame via the (unmodified) if bt_depth < depth: return None, bt_depth check, so the entire search for that puzzle terminates the first time an unrecoverable branch is hit — see Part 1's D row for the exact mechanics.
Instrumentation-only leak, found while auditing cascade internals

Conditions C and D leak an internal bookkeeping key _live_explore_counter into their final per-puzzle JSON (both benchmarks) — B strips it, A never sets it, C/D never strip it. It is not read by summarize_backtracks() or the concise crossword summary, so it does not affect any reported metric or the search itself. It will show up as a stray, all-NaN-for-A/B column if you pd.json_normalize the raw detailed logs across all four conditions. See Part 6.

Everything else below is a full walkthrough of the code, metric-by-metric, condition-by-condition, so you can verify these claims yourself against the file:line references given throughout.

Condition D — exact rule (not inferred from the name)

From _strict_nonparent, dfs.py:917-1014:

  1. If from_depth <= 1: no model call, immediately UNRECOVERABLE (there is provably no legal non-parent target).
  2. Otherwise the model sees STRICT_NONPARENT_BACKTRACK_PROMPT, which explicitly forbids the immediate parent and asks for either ANSWER: <n> or UNRECOVERABLE.
  3. A returned <n> is only accepted if 0 <= n <= from_depth − 2 (i.e. strictly above the parent) — _parse_strict_response, dfs.py:894-914. An out-of-range or parent-equal answer is rejected and reclassified as unrecoverable, never silently clamped to the parent.
  4. On UNRECOVERABLE, the function returns the sentinel −1. Because −1 < depth for every real depth ≥ 0, the existing (unmodified) propagation check if bt_depth < depth: return None, bt_depth fires at every enclosing recursive frame, all the way to the top-level call in solve_dfs_nonparent_strict, which then returns sol=None. The search for that puzzle ends there — no further siblings at any level are tried. This is not a bounded local backtrack; it is a full-search abort triggered by one unrecoverable dead end anywhere in the tree.

Practical implication: puzzles where D goes unrecoverable early will show markedly fewer nodes_explored / candidates_evaluated than A/B/C on the same puzzle, purely from early termination — not from D "searching less efficiently." Report num_unrecoverable alongside success rate for D so this isn't misread as inefficiency.

Part 4Metric definitions — exact mechanics, not variable names

nodes_explored

Game24 A (dfs.py:348-351): computed up front, in one batch, from the full ranked candidate list — n_pass = sum(1 for _,v in ranked if v > v_th), added before the loop even runs. This means it counts candidates that scored above threshold, not candidates whose subtree was necessarily recursed into — if the loop returns early on a found solution or the budget runs out mid-loop, some counted "passes" never actually got their recursive call. This is a deliberate design choice (stated in the code's own comment, dfs.py:337-347) to make candidates_evaluated == nodes_explored + candidates_pruned hold exactly even under early returns.

Game24 B/C/D (dfs.py:540-542): identical up-front-batch definition, same rationale, computed from valid = [(p,v) for p,v in ranked if v > v_th].

Crosswords (all four) (dfs_crossward.py:198-201): incremented one at a time, inside the loop, only for a candidate that has already been committed (env.step already applied, node_budget already decremented) and is about to be recursed into or terminally recorded. This is a tighter, literal "state actually visited" count.

Implication

nodes_explored is directly comparable across A/B/C/D within each benchmark (identical definition used by all four conditions of that benchmark) but is not the same concept across benchmarks — Game24's number can include candidates that were scored but never actually recursed into on an early-return path; the crossword number cannot. Don't pool Game24 and crossword nodes_explored into one combined statistic.

candidates_evaluated

Counts every candidate that reached the value/confidence-scoring step, before the pruning decision and before the node_budget decrement — it is fixed the moment get_values() (Game24) or the propose call's confidence vote (crosswords) returns, for the entire ranked list at that node, regardless of how many of them the subsequent loop actually processes. Identical definition and increment point across A/B/C/D within each benchmark.

candidates_pruned

A candidate is "pruned" if it is present in that node's ranked list but did not end up counted in that node's nodes_explored contribution — i.e. candidates_pruned (this node) = len(ranked) − nodes_explored (this node), computed as one subtraction after the loop, not accumulated incrementally per rejection. In Game24 this equals "scored ≤ v_th." In crosswords this equals "either the env.status check failed (crossing-constraint violation) or the max_per_state cap was reached" — until the recent off-by-one fix, a capped-out candidate could vanish from both counts; it is now correctly counted here.

backtracks

One raw entry in info['backtracks'] = one dead-end event at one node: either a rejected/failed candidate (A) or one call to the active backtrack_fn (B/C/D). A β(c) cascade is counted as multiple raw backtrack events — each individual model call that returns "still inside the failed subtree" (zero new candidates explored since the last call) gets its own raw entry, tagged cascade=True and sharing a cascade_id with the chain it belongs to. collapse_cascades() (dfs.py:66) then merges each maximal run of same-cascade_id events into one logical backtrack, reported separately as num_logical_backtracks / backtracks_merged. Both the raw and merged views are always available side by side; nothing is discarded.

jump

jump = from_depth − to_depth, computed once per backtrack event at the moment the target is chosen. For D's unrecoverable events, jump is explicitly None (never a fabricated 0 or negative number) and is filtered out of the mean/percentage calculations in summarize_backtracks, while still being counted in the raw event total.

success

Game24 (game24.py:114-131): verify_steps() re-simulates the arithmetic from the puzzle's original 4 numbers against the model's own "a op b = c (left: ...)" trace lines, checking each step consumes real remaining numbers and that the pool ends at exactly [24]. This does not trust a separately-generated "Answer: ..." line — it only re-derives arithmetic the model already committed to in its trace. Falls back to parsing a final expression line only when no step trace exists at all (e.g. a naive-baseline run, not applicable to any DFS condition here).

Crosswords (crosswords.py:190-202): test_output re-parses the returned board-grid string back into per-row actions and steps a fresh env through them, producing r_word (fraction of the 10 answer slots matching ground truth), r_letter (fraction of 25 letters matching), and r_game (exact full-board match, the true "solved" boolean). The 'r' key that feeds run.py's printed running average is set to r_word, not r_game — the console summary during a run is therefore a graded word-accuracy average, not a solved/unsolved rate. The per-puzzle detailed log and concise summary both separately carry r_game as the actual boolean.

Part 5Final crossword output selection

What's returned by default

The deepest explored state, first-encountered on ties — select_final_state(node_snapshots, method='deepest'), called identically from all four solve_dfs_crossword* functions with selection_method defaulting to 'deepest' unless --selection_method best_r_word is explicitly passed.

Tie-breaking

Yes — Python's max() keeps the first element on a tied key, and depth is derived from len(n['actions']), which increases strictly in visitation order, so "first encountered" and "first in the list" coincide. Verified live: a run with a genuine 3-way tie at max depth correctly returned the first-explored of the three.

  1. What state is returned? The node_snapshot with the greatest len(actions).
  2. Is it the deepest explored state? Yes, by default.
  3. Is it r_word-based best state? No, not by default — that path exists (method='best_r_word') but is opt-in only, and a live smoke test confirmed it selects a genuinely different (shallower) state than 'deepest' when r_word and depth disagree.
  4. Tie-breaking rule? First-encountered, confirmed above.
  5. Is r_word still retained for the oracle ablation? Yes — every snapshot always carries r_word, r_letter, r_game regardless of which selection method is active; nothing about recording it was removed.
  6. Faithful to the paper's main ToT-DFS result? Yes, as of this session's fix — the port previously used r_word-based best-state selection (matching the paper's separate oracle "+best state" ablation, not its main reported DFS number). The main path now matches the paper's stated "render the deepest explored state" methodology.

Part 6Cascade instrumentation audit

  • cascade=True criterion (dfs.py:655-658, identical in dfs_crossward.py:386-389): a β(c) model call is a cascade iff there was a previous β(c) call in this puzzle (prev_snapshot is not None) and zero new node-budget-consuming candidates were explored since it (explore_count == prev_snapshot), where explore_count is a dedicated counter _live_explore_counter incremented once per candidate actually committed to inside _diligent_recurse's loop — a real-time counter, distinct from the batch-computed nodes_explored.
  • "Explored since previous β(c)" = the delta between the live counter's value now and its snapshot at the previous β(c) call; stored per-event as explored_since_previous_beta, None on the very first call.
  • Behaviorally inert? Yes. Cascade tagging only writes metadata into info['backtracks'] entries and a handful of underscore-prefixed bookkeeping keys on info itself. Nothing about cascade status is read by any branch of the search logic (_diligent_recurse/_diligent_recurse_crossword never inspect cascade).
  • Affects node-budget accounting? No — _live_explore_counter is a separate counter from node_budget[0] and nodes_explored; it exists purely to detect cascades.
  • Raw vs. merged representation — as described in Part 4's backtracks section: raw events keep every individual β(c) call; collapse_cascades() produces a read-only, purely-derived merged view alongside it, never replacing the raw list.
  • Can A, C, or D legitimately have beta/cascade metrics? A: no (never calls a backtrack_fn at all — parent-return is inline). C: no (_fixed_k2 never sets cascade/cascade_id/etc., and explicitly documents this in its own docstring). D: no (_strict_nonparent likewise never sets these keys) — even though D does call the LLM, its "recoverable-target" calls are architecturally distinct from B's cascade concept and were deliberately not wired into it.
  • Are they correctly treated as N/A rather than 0? Mostly yes, with one caveat. summarize_backtracks() reports beta_calls=0, num_cascaded_calls=0, pct_cascaded_calls=0.0 for A/C/D — a true zero is the correct value here (zero cascade-tagged events genuinely occurred), so this is not a mislabeling, just worth remembering that "0" means "the concept doesn't apply" for A/C/D and "zero cascades observed" for B. The caveat: the leaked _live_explore_counter key (Part 2/summary) is not zeroed or removed for C/D — it's a stray non-zero internal counter sitting in the raw JSON with no corresponding cascade computation reading it, which could look like "a cascade counter exists for C/D" if inspected superficially. It doesn't feed any reported statistic.
  • Available for both Game24 and Crosswords? Yes — _beta/_beta_crossword implement the identical mechanism, and summarize_backtracks is the single shared function (imported into dfs_crossward.py) used by both benchmarks, so cascade statistics are computed the same way and are genuinely comparable across benchmarks — unlike nodes_explored (Part 4), this one is safe to compare Game24-vs-crossword.
